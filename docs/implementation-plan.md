# 구현 단계 설계

상태: 구현을 위한 설계 제안. 작성 기준: 2026-10-14. 이 문서의 디렉토리, API, 명령, 설정 파일은 구현 예정 구조이며 현재 실행 가능한 기능이 아닙니다.

관련 문서: [입출력 규격 후보](io-spec-candidates.md), [저장소별 호환성 검토](repository-compatibility.md).

## 1. 첫 버전의 목표

두 참가자를 대상으로 한 규칙 프로파일에서 총 1,000대국 이상을 완료합니다. 게임 상태 갱신·합법 수 판정·모델 입력 변환·로봇 추론과 행동 선택을 GPU에서 이어갑니다. 전체 탐색 로봇을 참가자로 등록할 때는 탐색까지 GPU에서 실행하는지 별도로 검증합니다.

첫 버전은 단일 프로세스, 단일 NVIDIA GPU, 단일 CUDA 스트림, 고정 배치 용량으로 구성합니다. 대회 설정과 파일 저장은 CPU가 담당합니다. CPU 판정 참조는 GPU 정확성을 검증할 때 사용합니다.

설계 중 읽기 조회한 개발 장치는 RTX 3050, VRAM 8,192 MiB, 드라이버 566.14입니다. Python 명령은 WindowsApps 경로였으며 `nvcc`, `cl`, `cmake`는 현재 PATH에서 발견하지 못했습니다. Python·PyTorch·CUDA 라이브러리의 실행 가능성은 아직 확인하지 않았습니다. 이 정보는 개발 환경의 관찰값이며 지원 환경을 고정한 선언이 아닙니다.

총 대국 수 `N`과 동시 배치 용량 `Bcap`은 별개입니다. 예를 들어 `N=1000, Bcap=128`이면 종료 슬롯에 다음 경기를 배치하여 총 1,000대국을 처리합니다. 8GB 장치에서 1,000개의 탐색 트리를 동시에 유지할 수 있다고 가정하지 않습니다.

## 2. 구현 기준과 선택 사항

| 항목 | 설계 제안 |
|---|---|
| 초기 보드·행동 | 9×9, `0..80=row*9+col`, `81=패스`, 기권은 별도 status |
| 공통 규칙 | 사용자 선택 확정: Alpha-Yoo 기본 규칙을 참조한 `gk-alpha-default`, 버전 1 |
| 데이터 계약 | 기존 `ObservationBatch`, `ActionBatch`; 정확한 v1 계약은 P0에서 문서화 |
| GPU 주 경로 | Python + PyTorch + 본 저장소 CUDA C++ 커널, CuPy NVRTC 실행기 |
| 내부 상태 | 정수 배열과 별도 생명주기 필드. 공통 경계는 uint8 보드·소유권 |
| 추론 | 평가 모드, 첫 비교는 FP32. 모델 구조·가중치·전처리·탐색 설정 식별 |
| 배치 | 고정 `Bcap`과 `valid`, 로봇별 유효 행 마스크 |
| 결과 | GPU에서 경기별 결과를 보존하고 CPU로 묶어서 회수 |
| 후속 확장 | 배치 압축, 트리 재사용, 다중 스트림, 별도 프로세스, 네트워크 게이트웨이 |

CuPy `RawModule`은 CUDA 소스를 NVRTC로 컴파일하고 커널을 조회할 수 있습니다. PyTorch가 상태·출력 버퍼를 소유하고 CuPy는 DLPack view와 공유 스트림으로 커널을 실행하도록 설계합니다. 정확한 PyTorch·CuPy·CUDA 버전은 P0의 드라이버 호환 점검 후 고정합니다. [RawModule](https://docs.cupy.dev/en/stable/reference/generated/cupy.RawModule.html), [CuPy/PyTorch 연결](https://docs.cupy.dev/en/stable/user_guide/interoperability.html)

외부 Alpha-Yoo의 runtime을 직접 실행하거나 커널 레이아웃을 공통 규격으로 고정하지 않습니다. 외부 결과물의 모델 구조·소스 revision·가중치는 읽어 확인하고, 실행에 필요한 어댑터와 코드·자산 사본은 이 저장소 안에서 관리합니다. 필요한 코드·자산의 사용 조건과 출처도 함께 기록합니다.

## 3. 모듈 구조

아래는 예정 구조입니다. P0·P1부터 필요한 파일만 단계별로 추가합니다.

```text
pyproject.toml
src/gk_battle/
  bootstrap.py                  # 프로젝트 안의 캐시·출력 경로 설정
  cli.py                        # 진단, 소규모 대국, 대회, 벤치마크
  contracts/
    batches.py                  # 관측·행동·결과 계약
    participant.py              # 참가자 manifest, 기능 협상
    validation.py               # 구조·dtype·값·규칙 지원 검증
  rules/
    profile.py                  # 버전과 내용 hash를 가진 규칙
    cpu_reference.py            # 독립 CPU 판정 참조
  gpu/
    runtime.py                  # NVRTC, device·stream·버퍼 view
    state.py                    # GPU 상태와 경기 생명주기
    kernels/
      rules.cu                  # reset, legal, step, score
      encode.cu                 # 모델별 특징 생성
      select.cu                 # 정책 종류별 마스킹·행동 선택
      schedule.cu               # 차례 마스크, 경기 배치·슬롯 교체
  adapters/
    alpha_yoo.py                # 10채널, logits, GPU 로봇 경계
    lsm107.py                   # 5채널, log_probs, native CPU 경계
    discord_format.py           # 좌표·명령·기보 변환
  actors/
    baseline.py                 # 결정적 최소 로봇
    policy.py                   # GPU 정책으로 직접 행동 선택
    search.py                   # 검증된 GPU 탐색 참가 경계
  runner/
    requests.py                 # 요청·응답·경기 버전 매핑
    arena.py                    # 배치 실행과 자원 수명
  results/
    ledger.py                   # 경기별 결과, 중복·누락 검사
    writer.py                   # 결과와 선택 기보 저장
  transports/                   # 후속 이진 프로그램 연결
  gateways/                     # 후속 Discord·TCP 연결
configs/rulesets/
participants/                   # 참가자 manifest
artifacts/                      # 모델 가중치와 실행 자산
tests/{contracts,rules,adapters,integration}/
tests/fixtures/                 # 독립 상태·기보·예상 결과
benchmarks/
runs/                           # 결과·설정·로그·성능 측정
.runtime/                       # JIT·라이브러리·임시 캐시
```

| 경계 | 책임 | 대표 API 후보 |
|---|---|---|
| `RulesBackend` | 초기화, 관측, 합법 수, 행동 적용, 종료 판정 | `reset`, `observe`, `apply`, `results` |
| `PolicyAdapter` | 공통 상태→native 특징, native 정책→선택기 입력 | `encode`, `evaluate`, `normalize` |
| `DecisionActor` | 한 국면당 최종 행동 선택; 전체 탐색은 내부 책임 | `act(observation, context) -> ActionBatch` |
| `RequestTracker` | 세션·요청과 경기 ID·버전 결합 | `issue`, `validate_response`, `consume` |
| `ArenaRunner` | 회차 대상 고정, 실행, 슬롯 교체, 결과 회수 | `run(match_spec) -> RunReport` |
| `ResultSink` | 참가 설정과 결과 저장, 완료 수 검증 | `write_batch`, `finalize` |

공통 규칙 엔진은 모든 최종 행동을 다시 검증합니다. 모델별 어댑터는 임의로 규칙·승패를 바꾸지 않습니다. 게임 규칙의 종료 사유와 대회 운영상 기권·오류·중단 사유는 별도 필드로 관리합니다.

## 4. 상태·요청·버퍼 수명

### 경기와 요청 식별

- 경기 identity는 `session_id + game_id`입니다. 슬롯 번호는 identity가 아닙니다.
- 요청은 `session_id + request_id`로 식별합니다. 요청 당시 `row → (game_id,state_revision)`을 별도 배열로 고정합니다. GPU 경로에서는 이 배열도 GPU에 보존하여 매 요청 전체 ID를 CPU로 복사할 필요가 없도록 합니다.
- `state_revision`은 수락된 착수·패스, 기권·시간초과 등 엔진이 적용한 종료 판정에서 증가합니다. 거부한 응답은 상태를 바꾸지 않습니다. 무효 수를 패배로 판정하는 설정에서는 무효 수 자체 대신 그 종료 판정이 버전을 바꿉니다.
- 알 수 없는 요청, 중복 응답, 오래된 경기 ID·버전, 잘못된 shape는 적용하지 않습니다. 정상 배치 안의 행별 실패는 해당 경기의 오류로 분리합니다.
- 초기는 경기당 동시에 하나의 논리적 행동 요청만 허용합니다. 같은 요청의 재시도는 같은 결정 ID와 난수 상태를 사용합니다.

### 종료와 슬롯 재사용

```text
EMPTY → RUNNING → FINISHED / FAILED / TRUNCATED → RECORDED → EMPTY
```

`FINISHED`는 게임 규칙 또는 명시된 기권·시간초과 판정으로 완료된 경기, `FAILED`는 실행·계약 실패, `TRUNCATED`는 수 제한·운영 중단입니다. 상태가 달라진 경기 결과를 정상 승률 집계에 포함할지는 대회 설정으로 명시합니다.

종료 결과와 경기 identity를 결과 저장 영역에 복사한 뒤, 해당 경기의 요청·버퍼 소비가 끝나야 슬롯을 재사용합니다. 새 경기에는 새 ID, 초기 상태, seed, revision을 부여하고 로봇의 캐시·탐색 트리를 초기화합니다.

첫 버전은 `N`개 경기 각각의 결과 행을 GPU에 사전 할당합니다. 슬롯 재사용과 무관하게 결과 행을 보존합니다. CPU 저장 시 동일 경기 ID·동일 내용의 재전송은 멱등 처리하고 상충하는 결과는 오류로 처리합니다. 추가 경기 작업을 예약하는 경우 별도 결과 chunk를 할당하여 기존 결과를 덮어쓰지 않습니다. 결과 버퍼를 원형 큐로 바꾸는 최적화는 overflow와 역압 처리를 추가한 뒤 도입합니다.

### 유효 행과 난수

`valid=false` 행은 행동 선택·RNG 소비·경기별 캐시 갱신·탐색 트리·경기 상태 변경에서 제외합니다. 고정 크기 신경망이 더미 행도 계산하는 것은 허용하되 유효 행의 결과에 영향을 주지 않는 모델 계약을 요구합니다. 더미 입력·마스크의 NaN 처리와 패딩 계산 비용을 검증합니다.

전부 거짓인 마스크에는 일반 softmax·샘플링을 그대로 적용하지 않습니다. 종료·패딩 행은 무시하고, 진행 중 행에 합법 수가 없으면 규칙 또는 계약 오류로 처리합니다. 잘못된 행동을 자동 패스로 바꾸지 않습니다.

난수는 경기 ID·참가자·논리적 결정 번호에 연결하고 슬롯 번호와 배치 순서에 의존하지 않게 설계합니다. seed와 RNG counter를 기록합니다. 이 계약이 GPU 부동소수점 결과의 배치 크기 간 비트 단위 동일성까지 보장하는 것은 아니므로 재현 조건에는 배치·정밀도·라이브러리 버전도 기록합니다.

초기 캐시·탐색 트리는 상태 버전 변경 때 비우는 단순 정책으로 검증합니다. 트리를 재사용하려면 양쪽의 실제 적용 행동과 새 버전을 통지하는 계약을 추가하고, 결과물 식별 정보에도 재사용 설정을 포함합니다.

### GPU 버퍼와 스트림

엔진은 상태를, 요청은 관측 staging을, 로봇은 출력을, 결과 저장기는 결과 배열을 소유합니다. DLPack view의 원본과 스트림을 소비 완료까지 유지합니다. 처음에는 모두 같은 스트림에 순서대로 enqueue합니다.

다중 스트림을 추가할 때는 관측 준비, 관측 소비, 행동 준비, 상태 갱신, 결과 복사 완료 이벤트를 명시합니다. 다른 스트림에서 쓰는 PyTorch 버퍼의 할당 수명도 관리해야 합니다. [PyTorch CUDA stream·memory semantics](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-streams)

## 5. 배치 실행 루프

1. 회차 시작 시 진행 중 경기와 현재 차례로 각 로봇의 `valid`와 예상 상태 버전을 GPU에서 고정합니다.
2. 그 스냅숏을 기준으로 합법 마스크와 로봇별 입력을 생성합니다.
3. 각 로봇을 호출하고 이번 회차의 행동·status 배열을 채웁니다.
4. 요청·경기 버전, 행동 범위, status, 합법성을 검증하고 경기마다 최대 한 번 행동을 적용합니다.
5. 종료 결과를 기록하고 소비가 끝난 슬롯에 다음 경기를 초기화합니다.
6. 정해진 회차 간격 또는 실행 종료 시 결과·오류 집계만 CPU로 회수합니다.

A의 행동 적용 뒤 차례를 다시 읽어 같은 회차의 B 대상에 넣지 않습니다. 두 로봇의 대상은 적용 전에 고정하며 한 경기 안의 상태 전이는 순서대로 수행합니다.

첫 구현은 고정 `Bcap`으로 시작합니다. 가변 길이 `torch.nonzero` 압축은 CUDA 입력에서 CPU 동기화를 일으킬 수 있으므로 P6의 측정 후 최적화로 둡니다. 후속 압축은 GPU index·count와 고정 크기 bucket, gather/scatter 비용까지 비교합니다. [torch.nonzero](https://docs.pytorch.org/docs/main/generated/torch.nonzero.html)

## 6. 단계별 구현과 통과 조건

| 단계 | 구현할 결과물 | 통과 조건 |
|---|---|---|
| **P0 계약·환경** | 첫 ruleset 문서, v1 배치·참가자 계약, 환경 진단·bootstrap, 모델 자산 목록 | 규칙 선택과 예제가 명확하고 CUDA 버전 조합·쓰기 경로가 검증됨 |
| **P1 CPU 참조·변환** | 독립 CPU 판정, 계약 검증기, 결정적 최소 로봇, 좌표·정책 변환기 | 정상·오류 수순, 종료, 상태 보존, 좌표와 정책 의미 검증 통과 |
| **P2 GPU 규칙** | reset·legal·step·score 커널, 상태 버퍼·관측 생성 | 매 수마다 CPU와 보드·소유권·차례·합법 마스크·재고·패스·수락 여부·종료·점수 일치 |
| **P3 GPU 정책 참가** | Alpha 10채널·LSM 5채널, logits/log_probs 선택기, 실제 가중치 loader | 입력 채널과 정책 의미 일치, 실제 자산으로 배치 추론·합법 행동 검증 |
| **P4 대회 실행기** | 요청·슬롯 수명, 선후 교대, 결과 ledger·CLI | 소규모 전체 대회가 중복·누락 없이 종료, 지연·오류·재사용 사례 통과 |
| **P5 전체 GPU 로봇** | GPU 탐색 참가자 또는 이 저장소의 검증된 GPU 탐색 경계 | 탐색 주체·예산·가치 관점이 명확하고 CPU 탐색이 해당 모드에 섞이지 않음 |
| **P6 1,000대국·최적화** | 실제 실행 결과, 단계별 성능·VRAM·전송 보고서 | 실패·중단을 제외한 집계 대상 완료 대국이 최소 1,000개이고 환경·자산·설정과 결과를 보존 |
| **P7 이진 호환·게이트웨이** | 별도 프로그램 연결, native CPU 로봇, Discord/TCP 변환·연동 | 각 역할·실행 범위·지원 수준이 검증되고 실패가 정상 결과에 섞이지 않음 |

P3·P4의 직접 정책 선택은 기존 전체 MCTS 로봇 평가와 별도 참가 모드입니다. 전체 GPU 탐색 결과를 비교하려면 P5까지 완료해야 합니다. P7까지 기다리지 않아도 GPU 주 경로의 대회와 벤치마크를 완성할 수 있습니다.

### P0: 규칙·참가자·실행 환경

규칙 문서에는 초기판, 중립 칸, 연결 방향, 양쪽 집 착수, 영구 소유권, 재고, 포획과 자충수 우선순위, 포획 후 보드, 연속 패스, 점수·동점, 종료 후 차례와 입력 처리를 명시합니다. 규칙 문서의 버전과 내용 hash를 기록하고 서로 다른 native 규칙을 같은 ID로 등록하지 않습니다. 1,000대국 목표의 기본 집계 대상은 게임 규칙 종료와 정상 기권이며 실행 실패·시간초과·수 제한·중단은 제외합니다. 다른 집계 정책은 비교 조건으로 명시합니다.

사용자가 2026-10-14에 **Alpha-Yoo 기본 규칙을 참조한 첫 프로파일**을 선택했습니다. `gk-alpha-default`, 버전 1을 [규칙 명세](rulesets/gk-alpha-default-v1.md)와 [프로파일 JSON](../configs/rulesets/gk-alpha-default-v1.json)에 기록했습니다. 기준은 41개 재고, 중앙 중립 돌, 양쪽 완성 집 착수 금지, 집 소유권 유지, 상대 포획 우선, 자충수 수락 후 패배, 두 번 연속 패스 종료, 선공 집이 3칸 이상 많을 때 선공 승리입니다. 원본 참조 커밋을 고정하며 추후 원본 변경을 자동 반영하지 않습니다. 규칙 선택은 완료됐고 P0의 나머지 계약·환경 검증과 CPU/GPU 구현은 별도 작업입니다.

참가 manifest에는 역할, source revision, 어댑터 버전, 지원 ruleset, 모델 구조, 가중치 경로·SHA-256, 특징 계약, 정책 종류, 가치 관점, 탐색 설정, 실행 범위·예산을 기록합니다. 자산이 없거나 구조가 맞지 않으면 준비 완료로 표시하지 않습니다. 최소 로봇으로 실행기 검증은 진행할 수 있습니다.

라이브러리 import 전에 프로젝트 안의 `.runtime/`으로 `CUPY_CACHE_DIR`, `CUDA_CACHE_PATH`, `TEMP`, `TMP`, 필요한 모델·확장 캐시 경로를 지정합니다. Python bytecode 생성도 차단하거나 프로젝트 내부로 지정합니다. 외부 Alpha 경로를 작업·출력 디렉토리로 쓰지 않습니다. [CuPy 캐시 설정](https://docs.cupy.dev/en/stable/reference/environment.html#cupy-cache-dir), [CUDA 캐시 설정](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-cache-path), [Python bytecode 설정](https://docs.python.org/3/using/cmdline.html#cmdoption-B)

### P1·P2: 규칙 정확성

고정 사례부터 검증한 뒤 재현 가능한 합법·불법 수순으로 CPU/GPU 차등 검증을 확대합니다. 임의의 보드로 상태를 만들 때는 소유권·재고·패스 이력도 명시하여 도달 가능한 상태와 분석용 상태를 구분합니다.

필수 사례는 초기판, 중립·점유 칸, 양쪽 집 착수, 영구 집 유지, 재고 소진, 가장자리 집, 단일·복수 포획, 동시 포위, 자충수, 패스 뒤 거부된 착수, 두 패스 종료, 종료 뒤 입력입니다. 정수 상태와 결과는 완전히 일치해야 합니다.

GPU 연결 영역 탐색은 81칸의 유한 scratch와 명시적 stack/queue로 구현합니다. 경기별 단순 커널로 정확성을 확보하고 thread block 협력이나 bitboard는 P6에서 비교합니다. 장치 재귀·동적 할당을 초기 구현에 요구하지 않습니다.

### P3·P5: 실제 AI 결과물

Alpha는 10채널과 logits, LSM은 절대 5채널과 log_probs의 입력·출력 계약을 구현합니다. 특징과 합법 마스크를 GPU에서 생성하며 FP32 비교 허용오차는 테스트에서 명시합니다. int64 행동은 범위 검사 후 공통 int32로 변환합니다.

LSM의 가치 관점은 아직 확정되지 않았으므로 첫 정책 참가 모드에서는 value를 사용하지 않습니다. 관점 검증 전에는 그 값을 공통 PUCT에 넣지 않습니다. LSM 원래 CPU MCTS는 native 규칙을 포함한 별도 호환 모드이며, 최종 행동 마스킹만으로 내부 탐색이 공통 규칙을 따른다고 선언하지 않습니다.

전체 GPU 탐색은 실제 적용 규칙, node 상한, simulation 예산, tree overflow 처리, 입력·출력 계약을 검증합니다. 메모리는 모델·활성값 외에 `Bcap × node_cap × 노드·행동 edge 크기`를 별도로 산정합니다. 예산 부족을 조용히 다른 설정으로 바꾸지 않고 참가 설정과 결과에 기록합니다.

### P4: 대회와 오류 처리

처음에는 두 참가자의 단일 ruleset 대회를 구현합니다. 선후 교대, 경기별 seed, 참가 설정과 예산을 사전에 생성하고 재현 파일에 저장합니다. 다수 참가자는 이 대회 단위를 조합하는 후속 작업으로 연결합니다.

지연·중복·역순 응답, 슬롯 교체 후 이전 응답, 일부 행 실패, 전체 요청 실패, 기권, 수 제한, 전부 패딩인 호출, 결과 저장 재시도를 검증합니다. 같은 프로세스 GPU 호출을 중간에 안전하게 강제 종료하는 기능은 초기 시간 예산의 전제로 두지 않습니다. 초기 비교는 유한 simulation 예산을 우선하고, 엄격한 프로세스 timeout은 P7에서 분리합니다.

### P6: 실측과 최적화

동시 배치 용량 후보 `32,64,128,256,512,1000 또는 1024`를 실제 모델·탐색·VRAM에 맞춰 측정합니다. 모두 실행할 수 있다는 가정은 하지 않습니다. 실제 결과를 정상 완료·기권·오류·중단으로 나누고 P0에서 정한 집계 대상 완료 경기가 1,000개 이상이어야 통과합니다. 부족하면 설정된 추가 실행 상한 안에서 다음 경기를 예약합니다. 상한에 도달해도 부족하면 목표 미달로 보고하고 완료 기준을 낮추지 않습니다.

보고서는 환경·드라이버·라이브러리, source/weights hash, 규칙·예산·seed·정밀도, cold compile·warmup 시간, 전체 대회 시간, 완료 대국/초·국면/초, GPU 규칙·입력 변환·추론·탐색·회수 시간, peak allocated/reserved 및 프로세스 VRAM, CPU↔GPU 전송 횟수·바이트를 포함합니다.

GPU 구간은 이벤트로, 전체 대회는 시작부터 마지막 결과 완료까지의 벽시계 시간으로 측정합니다. CPU 함수 반환 시간만 추론 시간으로 쓰지 않습니다. [PyTorch CUDA 비동기 실행·측정](https://docs.pytorch.org/docs/main/notes/cuda.html#asynchronous-execution)

배치 압축, 버퍼 재사용 개선, 커널 융합, 다중 스트림, Graph, 비트 패킹, 혼합 정밀도는 병목을 측정한 뒤 각각 적용합니다. 의미·규칙·참가 설정의 보존을 확인하며 실제 개선과 메모리 비용을 함께 보고합니다. 속도 목표값은 최초 실측 후 결정합니다.

### P7: 네 저장소의 지원 범위 확대

| 대상 | 먼저 검증할 내용 | 후속 연결 조건 |
|---|---|---|
| Alpha-Yoo | 모델·GPU 상태·행동·전체 탐색 계약 | 실제 자산과 지원 ruleset, 읽기 전용 원본 보호 |
| LSM107 | 5채널·로그 확률·정책 참가 모드 | 전체 MCTS는 CPU/native 규칙 모드 또는 상태 전이까지 일치하는 별도 포팅 |
| Discord | 좌표·패스·기권·영토·기보 변환 | 네트워크 명령·이미지 출력은 대국 반복 경로 밖에서 처리 |
| kikuke | 패킷 codec와 방 ID 매핑 | panel 코드·좌표·pass/status 의미와 완전 상태 전달 계약 확인 |

이진 프로그램 연결은 little-endian 고정 너비, 프레임 길이, 배열 offset·shape, request ID와 최대 크기를 명시합니다. 잘린 프레임, 잘못된 크기, 종료·timeout·재시작을 검증하고 원래 프로그램의 stdout 로그와 프로토콜 채널을 구분합니다.

kikuke의 미확인 필드와 상태 방송 누락이 해결되기 전에는 완전한 게임 상태 연동을 지원한다고 선언하지 않습니다. 게이트웨이는 AI 참가자가 아니며, 메시지를 주고받았다는 사실만으로 대국 호환 검증을 통과시키지 않습니다.

## 7. 구현 시작 단위

첫 구현 작업은 **P0의 선택 사항 정리와 P1의 최소 공통 계약·CPU 참조·결정적 로봇**으로 구성하는 것을 권장합니다. 이후 P2 GPU 규칙, P3 실제 정책 참가자, P4 대회 실행기 순서로 연결합니다.

각 단계는 해당 검증을 통과한 산출물로 완료를 판단합니다. 이 문서 작성만으로 runtime 설치, 규칙 구현, 모델 추론, 호환 대국 또는 1,000대국 벤치마크가 완료된 것은 아닙니다.
